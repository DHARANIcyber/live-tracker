# College Bus Live Tracker System

A full-stack web application for live college bus tracking, student access, and transport management.

## Features
- Landing page with college information and transport metrics
- Bus search by bus number or route number
- Live tracking map with real-time GPS updates
- Admin, driver, and student dashboards
- REST API endpoints for buses, students, login, and GPS updates

## Setup
Install dependencies from the project root and build the frontend before running the combined server:

```bash
npm install
npm --prefix backend install
npm --prefix frontend install
npm --prefix frontend run build
npm start
```

The combined server runs at `http://localhost:5000`. Copy `.env.example` to `.env` in the project root. When running the backend from its own directory, place the same variables in `backend/.env` instead.

For frontend-only development, run the backend with `npm --prefix backend run dev` and the frontend with `npm --prefix frontend start` in separate terminals.

## Driver GPS and Bus Assignments
- Login issues a signed 12-hour role token. Admin accounts can access management data, drivers can update GPS only for their assigned bus, and students can access only one profile. Local demo student login accepts the entered email after validating the student password; production requires an email registered on that student's profile.
- Set `AUTH_TOKEN_SECRET` to a long random secret in every production backend instance. Generate one with `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`.
- In production, set `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `STUDENT_EMAIL`, and `STUDENT_PASSWORD` on the backend. Local demo credentials are used only outside production; production login is disabled for a role when its matching environment variables are missing. The configured student email must match a student profile in the database.
- Driver login requires the phone number, password, and assigned bus number. If that bus is already assigned to another driver, login reports the conflict. In local non-production demo mode, the first phone to successfully sign in claims the seeded demo driver; production requires the driver's registered phone. GPS updates require the driver's token and are limited to their assigned bus.
- Set `MONGO_URI` for persistent buses, drivers, and GPS history. `GPS_LOCATION_TIMEOUT_MS` defaults to `45000`; buses without a recent valid fix are marked `OFFLINE` and their coordinates are omitted from live API responses.
- `DRIVER_BOOTSTRAP_EMAIL`, `DRIVER_BOOTSTRAP_PHONE`, `DRIVER_BOOTSTRAP_PASSWORD`, and `DRIVER_BOOTSTRAP_BUS_NUMBER` can be used together to provision a production driver. Store the password in the deployment secret manager, not in source control.
- For additional drivers, create a `Driver` document with `name`, unique lowercase `email`, unique `phoneNumber` (digits only, including country code), a `passwordHash` generated by `backend/services/driverAuth.js` (`hashPassword(password)`), and `busId` set to the assigned Bus document's ID as a string. Set that Bus document's `driverId` to the same Driver ID string. `Driver.busId` is unique, so one bus cannot be assigned to multiple drivers at once.
- Serve the application over HTTPS in production; browser geolocation requires a secure context.

## API Endpoints
- GET /health
- GET /college
- GET /dashboard-summary
- POST /login
- GET /api/buses
- GET /api/bus/:busNumber
- GET /api/students
- POST /api/gps/update (authenticated driver only)
- POST /api/gps/offline (authenticated driver only)
- GET /api/gps/status/:busNumber
- GET /api/gps/history/:busId
- POST /api/addBus
- POST /api/addStudent

## Deployment Notes
- Frontend: Vercel
- Backend: Render
- Database: MongoDB Atlas

## Notes
- Without `MONGO_URI`, non-production runs use offline seeded bus records and in-memory GPS history. No seeded coordinates are presented as live.
- When `MONGO_URI` is configured but the database is unreachable, API requests return a service-unavailable error instead of silently treating in-memory data as persistent.
